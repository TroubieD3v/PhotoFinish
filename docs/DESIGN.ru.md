# PhotoFinish — проектный документ

> **PhotoFinish** proves race conditions in web APIs: it fires synchronized requests with the HTTP/2 single-packet attack, checks a business rule you declare, and keeps the evidence. One binary, CLI + web UI + CI.

Статус: дизайн от 22.11.2026. Готовы этапы M0–M3: демо-магазин, движки, сценарии, инварианты и вердикты (команды `run`, `probe`, `import`, `demo`), отчёты JSON/SARIF/JUnit/HTML, Docker-образ, GitHub Action и конвейер релиза. Веб-интерфейс и первый релиз — этапы M4–M5.

---

## 1. Зачем

Гонки (race conditions) — одна из самых прибыльных тем в баг-баунти с 2023 года, после исследования PortSwigger «Smashing the state machine». Типичные находки:

- повторное применение купона;
- двойное списание или двойной вывод денег;
- превышение лимитов (попытки 2FA, инвайты, остатки на складе);
- гонки в многошаговых сценариях (смена email, подтверждение).

Обычные DAST-сканеры отправляют запросы по одному, поэтому гонок не видят. Сейчас их ищут руками в Burp (Turbo Intruder, группы в Repeater). Поставить регрессионный тест «эта гонка больше не воспроизводится» в CI командам некуда.

### Что уже есть (проверено 22.11.2026)

| Инструмент | Что делает | Чего не хватает |
|---|---|---|
| Turbo Intruder (Burp, 1,8k★) | эталонная реализация single-packet attack | нужен Burp, ручная работа, нет инвариантов и CI |
| h2spacex (Python, 230★), h3spacex (20★) | низкоуровневая библиотека single-packet для HTTP/2 и HTTP/3 | не продукт: нет сценариев, проверок, отчётов |
| race-the-web (Go, 638★) | параллельные запросы, есть API для CI | заброшен с 2022 года, нет single-packet |
| Deadheat (TS, 0★, октябрь 2026) | инварианты, CI, прокси перед Postgres для перестановки запросов | инструмент разработчика (white-box, только Postgres), HTTP/1.1, single-packet отложен |
| race.py, race-proof (0★, ноябрь 2026) | скрипты и прототипы | ранняя стадия |

**Наша ниша** — сочетание, которого нет ни у кого:
1. настоящий single-packet attack (HTTP/2) плюс last-byte sync (HTTP/1.1);
2. декларативный сценарий с проверкой бизнес-правила (инварианта);
3. вердикт с доказательствами;
4. запуск в CI;
5. работа снаружи (black-box) против любого стека.

## 2. Для кого

1. **Пентестер или баг-хантер.** Нашёл подозрительный эндпоинт, вставил сырой запрос из Burp, описал правило и получил доказательство с таймлайном для отчёта.
2. **Разработчик или AppSec-инженер.** Описывает рискованные операции (оплата, купоны, лимиты) сценариями и прогоняет их в CI на staging. Если гонка вернулась, сборка падает.
3. **Обучение и CTF.** Встроенный уязвимый демо-магазин и лаборатория в WebSec-Lab. Пригодится для тренировок VG Team.

## 3. Принципы

- **Доказываем, а не гадаем.** Находка — это только нарушенный инвариант. Ответ «200 OK дважды» сам по себе ничего не доказывает.
- **Честный отрицательный результат.** Мы не пишем «уязвимости нет». Пишем «не воспроизведено за N попыток при разбросе X мкс, движок Y» и объясняем, что могло помешать: фронтенд-прокси, статика, ограничение скорости.
- **Безопасно по умолчанию:**
  - запросы уходят только на хосты из явного списка;
  - бюджет запросов и скорости;
  - секреты в отчётах маскируются;
  - режим `--dry-run`.
- **Один бинарник.** Go, без рантаймов, UI встроен. Есть Docker-образ и GitHub Action.
- **Стиль портфолио:** графитовая тема, SARIF, демо-данные, EN/RU.

## 4. Как это работает

```
scenario.yaml ─► setup ─► warm-up ─► RACE (N копий, один пакет) ─► check ─► reset ─┐
                    ▲                                                               │
                    └──────────────────────── trials × T ◄─────────────────────────┘
                                         │
                                         ▼
                           verdict + evidence bundle (JSON/HTML/SARIF/JUnit)
```

1. **setup** — подготовка состояния: логин, создание корзины, выдача купона. Значения достаются из ответов по JSON-пути (`$.a.b[0]`), из заголовка (`header:Name`) или из кода ответа (`status`).
2. **warm-up** — прогрев соединения на стороне сервера: несколько безобидных запросов по тому же соединению. Так советует PortSwigger для целей за фронтенд-прокси.
3. **race** — N копий одного запроса или набор разных запросов (multi-endpoint race) отправляются выбранным движком.
4. **check** — проверочный запрос и выражение-инвариант на CEL над ответами гонки и проверки.
5. **reset** — возврат состояния перед следующей попыткой (необязательно).
6. Повтор T раз. Одного нарушения достаточно для вердикта VIOLATED.

## 5. Движки синхронизации

### 5.1 `h2` — HTTP/2 single-packet attack (главный)

Реализация по алгоритму из исследования PortSwigger, на собственном HTTP/2-фреймере (`golang.org/x/net/http2.Framer`). Сам автор исследования советует Go как удобный стек для этого.

1. TLS с ALPN `h2`, одно соединение, обмен SETTINGS.
2. **Предварительная отправка каждого запроса:**
   - без тела: HEADERS без флага `END_STREAM`, придерживаем пустой DATA с `END_STREAM`;
   - с телом: HEADERS и всё тело, кроме последнего байта; придерживаем DATA с последним байтом и `END_STREAM`. Отправить тело целиком и придержать только `END_STREAM` нельзя: часть серверов считает запрос завершённым по `Content-Length`.
3. Пауза около 100 мс, затем PING для прогрева локального стека.
4. **Финальные кадры всех потоков собираем в один буфер и отдаём одним `Write`.** Это одна TLS-запись размером меньше MSS. Трюк с алгоритмом Нейгла из оригинала нужен библиотекам, которые пишут кадры по одному. Нам он не нужен: финальные кадры и так уходят одной записью.
5. Каждый придержанный кадр занимает около 10 байт: 9 байт заголовка кадра DATA и последний байт тела (у запроса без тела кадр пустой). Поэтому одна запись до 1200 байт несёт около 100 потоков. Если финальных кадров больше, движок разбивает их на несколько записей по 1200 байт и меньше, а отчёт гонки говорит об этом (`release.writes` и примечание в `notes`).

### 5.2 `h1` — HTTP/1.1 last-byte sync

N соединений. По каждому уходит весь запрос, кроме последнего байта. Затем последние байты отправляются подряд в одном цикле. Нужен для целей без HTTP/2.

### 5.3 `burst` — наивный параллельный режим

Обычные горутины без синхронизации. Это базовая линия: отчёт показывает, насколько точные движки лучше на этой цели.

### 5.4 `auto`

По ALPN выбирает `h2`, иначе `h1`.

### 5.5 Позже (не в v0.1)

- **First sequence sync** (RyotaK, GMO Flatt Security, 2024): IP-фрагментация и придержанный первый TCP-сегмент, тысячи запросов одновременно. Нужны raw-сокеты и права администратора, только Linux, отдельный флаг.
- **HTTP/3** через quic-go.
- **Однопакетная отправка через фронтенд-прокси**, когда тот открывает новые соединения к бэкенду.

## 6. Сценарий

```yaml
version: 1
name: coupon-applied-twice
target: https://shop.example.test/api  # пути запросов добавляются к пути target
tls:
  insecure: false                      # true: не проверять сертификат (демо-магазин)
scope:
  allow_hosts: [shop.example.test]     # обязательно; всё остальное блокируется
  budget: { requests: 600, rps: 50 }

identities:
  alice:
    headers: { Authorization: "Bearer ${env:ALICE_TOKEN}" }

setup:
  - id: cart
    as: alice
    request: POST /carts
    expect_status: [201]
    extract: { cart_id: "$.id" }

race:
  engine: auto            # h2 | h1 | burst | auto
  copies: 20
  warmup: 3
  request:
    as: alice
    raw: |
      POST /carts/{{cart_id}}/coupons HTTP/2
      Content-Type: application/json

      {"code":"WELCOME10"}

check:
  as: alice
  request: GET /carts/{{cart_id}}
  invariant: >
    size(check.json.discounts) <= 1 &&
    size(race.filter(r, r.status == 200)) <= 1
  explain: "A single-use coupon must apply at most once per cart."

trials: 10
reset:
  - { as: alice, request: "DELETE /carts/{{cart_id}}" }
```

- **Инварианты на CEL** (`cel-go`, язык выражений Google). Он безопасный, без побочных эффектов, с понятными ошибками. Доступны только стандартные макросы (`filter`, `exists`, `all`, `map`, `size`), своих функций нет: число ответов с условием считается как `size(race.filter(r, ...))`, а не `race.count(...)`. Каждая часть верхнеуровневой цепочки `&&` вычисляется отдельно, и отчёт показывает её значение, например `3 <= 1`. Ошибка вычисления (нет ключа, не тот тип) даёт INCONCLUSIVE, а не VIOLATED.
- **`tls.insecure`** отключает проверку сертификата для всех запросов сценария. Нужен для самоподписанных лабораторных целей вроде демо-магазина; флаг `--insecure` у `run` делает то же самое.
- **Бюджет.** `requests` — общий лимит на весь прогон, в нём считается каждый запрос: setup, прогрев, гонка, check, reset (по умолчанию 1000). Когда лимит исчерпан, оставшиеся попытки пропускаются с пометкой в отчёте, а вердикт считается по выполненным. `rps` ограничивает только шаги setup, check и reset (token bucket без активного ожидания, по умолчанию 20): гонка — это один залп, и ограничивать её скорость значило бы её разрушить.
- **Сырой запрос** можно вставить прямо из Burp или DevTools: строка запроса, заголовки, пустая строка, тело. Заголовок `Host` игнорируется, адрес задаёт `target`. Поддерживается импорт HAR (`photofinish import`).
- **Секреты** берутся из окружения (`${env:...}`) и в отчётах маскируются вместе с заголовками identities, `Authorization`, `Cookie` и ключами JSON вроде `password` и `token`, в том числе в экранированном виде (JSON, percent-encoding) и в обрезанных телах ответов. Примеры для демо-магазина записывают его публичные демо-токены прямо в файл.

## 7. Вердикты

| Вердикт | Когда | Код выхода |
|---|---|---|
| `VIOLATED` | инвариант нарушен хотя бы в одной попытке с чистой гонкой | 1 |
| `HELD` | все T попыток прошли; в отчёте разброс отправки и ответов и вывод «не воспроизведено», а не «безопасно» | 0 |
| `INCONCLUSIVE` | не меньше половины попыток не удалось оценить: ошибки сети или нет ответа, ответы до отправки последнего кадра (признак статики), сработал лимит запросов (любой 429 в гонке; если сценарий задал `race.expect_429: true`, 429 без `Retry-After` и заголовков `RateLimit` считаются ответом приложения, например блокировкой 2FA, кроме гонки, где 429 вернули все запросы), неожиданный код ответа в setup, ошибка вычисления инварианта. Неполноценная гонка делает попытку INCONCLUSIVE, даже если инвариант ложен: нарушение на гонке, которая толком не состоялась, гонку не доказывает | 2 |
| `ERROR` | ошибка сценария, запрет scope или сбой setup до первой гонки | 3 |
| — | ошибка использования CLI: неизвестная команда, неверный флаг или аргумент (`EX_USAGE`, у всех команд, включая `demo`) | 64 |

Для нескольких сценариев `run` возвращает самый серьёзный код: 3, затем 1, затем 2, затем 0. Остальные команды (`probe`, `import`, `demo`) при ошибке выполнения возвращают 1.

## 8. Доказательства

Для каждой попытки сохраняем:

- **Таймлайн:**
  - момент предварительной отправки каждого потока;
  - момент финального `Write` (общий для всех кадров);
  - момент первого байта ответа по каждому потоку;
  - разброс ответов в микросекундах.

  Честная оговорка в интерфейсе: клиент не видит, когда запрос реально пришёл на сервер. Если цель возвращает свою метку времени (демо-магазин отдаёт `X-Arrival-Ns`), показываем и серверный разброс.
- Ответы гонки с кодом, заголовками и телом (с маскировкой), а также ответ проверки.
- Значения переменных и итог вычисления инварианта по шагам.
- Готовая команда воспроизведения: `photofinish run` с тем же сценарием, движком, числом попыток и копий.

**Форматы отчётов** (пакет `internal/report`, все строятся из одного `runner.Report`, поэтому маскировка одна на всех):
- JSON — полный пакет доказательств;
- HTML — для отчёта по баг-баунти: один самодостаточный файл без внешних запросов (встроенные CSS и SVG, системные шрифты), графитовая палитра со светлым вариантом; полоса статуса, таблица попыток, таймлайн первой попытки с нарушением и полоса прихода на сервер, инвариант по частям, ответ проверки, команда воспроизведения;
- SARIF 2.1.0 — для GitHub code scanning: правило `PF001` InvariantViolatedUnderConcurrency (error, security severity 7.5) на каждый сценарий VIOLATED и `PF002` RaceTestInconclusive (warning) на каждый INCONCLUSIVE, привязка к строке `check.invariant`, отпечаток `photofinish/v1`; сценарии ERROR — уведомления о выполнении, HELD — без результатов;
- JUnit — для CI: набор тестов на сценарий, тест на попытку; VIOLATED — `failure`, INCONCLUSIVE — `skipped`, ERROR сценария — `error`.

`run --out DIR` пишет JSON каждого сценария и общие `report.html`, `results.sarif`, `junit.xml`; `--format` с `--output FILE` выводит один документ по всем сценариям.

## 9. Интерфейсы

### CLI

```
photofinish run scenario.yaml... [--engine h2] [--trials 20] [--copies 20] [--insecure]
                                 [--out report/] [--format text|json|sarif|junit|html] [--output FILE]
                                 [--fail-on violated|inconclusive|never] [--quiet]
photofinish probe https://host/path [--insecure]   # TLS, ALPN, SETTINGS HTTP/2, RTT, заголовок прихода
photofinish import burp.txt|file.har [--har-entry N] [--output scenario.yaml]
photofinish serve                        # веб-интерфейс на 127.0.0.1:8080 (этап M4)
photofinish demo                         # уязвимый магазин на 127.0.0.1:8443 (h2 + TLS)
```

### Веб-интерфейс

Графитовая палитра как в остальных проектах. Ориентиры по виду: вкладка Network в DevTools (водопад) и Wireshark.

1. **Scenarios** — список сценариев с последним вердиктом.
2. **Editor**:
   - слева сырой запрос, как в Repeater;
   - справа шаги setup, check и reset;
   - снизу инвариант с проверкой синтаксиса на лету.
3. **Run** — главный экран:
   - **сверху** полоса статуса: цель, движок, копии, попытки, бюджет;
   - **слева** таблица попыток с вердиктом и разбросом;
   - **в центре** таймлайн выбранной попытки: по строке на поток; отметки «предварительная отправка», «финальный кадр», «первый байт ответа»; линия общего `Write`;
   - **справа** инвариант с вычисленными значениями и ответы.
4. **Reports** — история запусков и экспорт.

Макет экрана Run: [mockup-run.png](mockup-run.png).

### CI

- **GitHub Action** `TroubieD3v/PhotoFinish@v0` (тег появится с v0.1.0), составной (`action.yml` в корне):
  - входы `scenarios` (пути и шаблоны через пробел или с новой строки, раскрываются bash с `globstar`), `engine`, `trials`, `copies`, `insecure`, `fail-on`, `sarif`, `junit`, `html`, `version`;
  - ставит Go через `actions/setup-go`, затем `go install ...@<version или ref самого action>`; при `uses: ./` собирает checkout;
  - один прогон с `--out` во временный каталог, копирует SARIF, JUnit и HTML по путям из входов, пишет таблицу «сценарий | вердикт | итог» в сводку задания;
  - выходы `verdict` (самый серьёзный вердикт), `exit-code`, `report-dir`; последний шаг завершается с кодом по правилу `fail-on`;
  - загрузку SARIF в code scanning пользователь добавляет сам (`github/codeql-action/upload-sarif`, право `security-events: write`).
- **Docker-образ** `ghcr.io/troubied3v/photofinish`: distroless `static-debian12:nonroot`, без root, `ENTRYPOINT ["photofinish"]`, рабочий каталог `/work`; многоплатформенный (linux/amd64, linux/arm64), сборка кросс-компиляцией без эмуляции. Демо в контейнере: `demo --addr 0.0.0.0:8443 --expose` с публикацией `-p 127.0.0.1:8443:8443`.
- **CI самого проекта:** задания `go` (gofmt, vet, `test -race`, сборка, `version`, smoke-тест демо), `examples` (все примеры против демо: `-fixed` дают 0, `-vuln` дают 1, SARIF проверяется по официальной схеме, JUnit и HTML разбираются), `action` (action из checkout проходит на `-fixed`, падает с VIOLATED на `coupon-vuln`, с `fail-on: never` только отчитывается), `docker` (сборка образа, демо и сценарий в контейнерах). Находки демо остаются артефактами и не попадают в code scanning репозитория.
- **Релиз** по тегу версии `vX.Y.Z` (или `vX.Y.Z-pre`; переносимый тег `v0` релиз не запускает): тесты, бинарники для пяти платформ с README и LICENSE, `checksums.txt`, smoke-тест Linux-бинарника против демо, заметки из раздела `## [X.Y.Z]` в CHANGELOG.md (без раздела релиз падает), образ с тегами `X.Y.Z`, `X.Y`, `latest` и OCI-метками; для нового релиза без суффикса workflow переносит тег `v0` (мажорный) на него, если это новейший v0.x.y.

## 10. Демо-цель: уязвимый магазин

Встроен в бинарник (`photofinish demo`), HTTP/2 по TLS с самоподписанным сертификатом. Каждый эндпоинт есть в двух вариантах, `/vuln/...` и `/fixed/...`, по образцу WebSec-Lab:

| Сценарий | Уязвимая версия | Исправленная версия |
|---|---|---|
| Купон | проверка и запись отдельными запросами | `UPDATE ... WHERE used = 0` с проверкой затронутых строк |
| Перевод между счетами | чтение баланса, затем списание | атомарное списание с условием |
| Попытки 2FA | счётчик читается и пишется отдельно | атомарный инкремент с лимитом |
| Подарочная карта | многошаговая: активация и списание | транзакция с блокировкой строки |

Окно гонки в уязвимой версии можно расширить флагом `--window 5ms` (в интерфейсе подписано «искусственно расширено»). Без флага гонка тоже ловится, только реже. Это видно на сравнении движков.

Хранилище — SQLite (`modernc.org/sqlite`, без CGO), как в CloudGraph.

## 11. Безопасность самого инструмента

- **Scope.** Хост вне `allow_hosts` блокируется до соединения. Редиректы не выполняются автоматически.
- **Бюджет.** Общий лимит запросов и скорость, жёсткий стоп.
- **Маскировка.** Заголовки `Authorization`, `Cookie` и `Set-Cookie`, токены в теле.
- **`serve` слушает только 127.0.0.1.** Доступ по случайному токену, защита от CSRF и DNS rebinding (проверка `Host`/`Origin`).
- **SECURITY.md и README** с оговоркой: только для систем, где тестирование разрешено.

## 13. Тестирование

- **Unit:**
  - фреймер: все финальные кадры уходят одним `Write`, проверяется через подменённое соединение;
  - удержание `END_STREAM` и последнего байта;
  - CEL;
  - парсинг Burp и HAR.
- **Интеграционные против демо-магазина:**
  - на `/vuln` движок `h2` находит нарушение за T попыток;
  - на `/fixed` за те же T попыток нарушений нет;
  - то же с nginx и Caddy перед приложением.
- **Бенчмарк (docs/BENCHMARKS.md):** доля попыток с нарушением и разброс для `h2`, `h1` и `burst` на одной цели. Это главная цифра для README и статьи.
- **E2E UI на Playwright:** скриншоты и GIF для README, как в остальных проектах.

## 14. Этапы

| Этап | Что готово | Критерий |
|---|---|---|
| M0 | репозиторий, CI, демо-магазин в двух вариантах | `photofinish demo` поднимается, тесты зелёные |
| M1 | движки `h2`, `h1`, `burst`, команда `probe` | `h2` стабильно ловит купон на `/vuln`, бенчмарк показывает разницу движков |
| M2 | сценарии, CEL, trials, вердикты, JSON-доказательства | `photofinish run examples/*.yaml` даёт верные вердикты на `/vuln` и `/fixed` |
| M3 | SARIF, JUnit, HTML, Docker, GitHub Action | Action роняет сборку на `/vuln` (в CI это проверяет задание `action`) |
| M4 | веб-интерфейс (Scenarios, Editor, Run, Reports) | сценарий собирается и запускается из UI, таймлайн показывает попытки |
| M5 | документация EN/RU, скриншоты, GIF, релиз v0.1.0, статья | релиз опубликован, лаборатория-гонка в WebSec-Lab |

## 15. Не входит в v0.1

- first sequence sync, HTTP/3, gRPC;
- white-box-перестановка запросов к базе (это ниша Deadheat, не наша);
- обход защиты от ботов и CAPTCHA (не делаем никогда).
